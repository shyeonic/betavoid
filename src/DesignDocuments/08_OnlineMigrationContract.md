## 0. 항법 실행 경계 최신 결정

**확정**

이 절은 본 문서와 `05_CostEfficientAuthoritativeServerPlan.md`의 이전 선실행 설명보다 우선한다.

- 자유 수동 입력은 클라이언트에서 즉시 실행한다. 수동 비행은 오차를 허용하는 표시 상태이며 정지 전환과 경제 행위 경계에서 서버에 결산한다.
- 표준 자동항해와 하이퍼드라이브는 결정론적 액션이다. 클라이언트는 서버 응답 전 함선의 위치, 회전, 속도, 항법 phase를 변경하지 않는다.
- 결정론적 명령을 전송한 클라이언트는 목표 표식과 `pending` UI만 표시한다. 서버가 이동 계약을 수락하면 응답 계약을 서버 현재 시각으로 파생한 뒤 그 상태에서 렌더링을 시작한다.
- 서버가 명령을 거절하거나 제한 시간 안에 수락 사실을 확인할 수 없으면 해당 액션은 실행하지 않는다. 실패한 명령을 로컬 항로로 복원하지 않는다.
- 인위적인 고정 지연은 추가하지 않는다. 사용자가 느끼는 짧은 대기는 실제 요청-판별-응답 시간이다.
- 전송 결과가 불명확할 때 동일 mutation을 재전송하지 않는다. 같은 `clientActionId`의 receipt를 제한 시간까지 조회해 이미 수락되었는지만 판별한다.
- pending 중 수동 입력이 발생하면 수동 입력은 즉시 적용하고 pending 표시는 취소한다. START 판별이 끝난 뒤 서버에 계약이 생겼다면 `MANUAL_OVERRIDE`를 정확히 한 번 전송한다.
- `MANUAL_OVERRIDE`의 취소 위치는 서버 수신 시각의 계약 파생값이다. 수동 목표 속도는 명령에 포함하되 서버가 함선 성능 범위로 검증해 확정한다.
- 서버 응답 또는 재접속 동기화 시 클라이언트는 서버 기준점으로 변경한다. 서버 상태가 경제 및 영속 위치의 최종 권위다.

## 1. 목적

beta-void의 온라인 전환은 기존 기능을 일반적인 온라인 게임 구조로 다시 만드는 작업이 아니다.

온라인 전환의 기본 의미는 다음과 같다.

> 기존 코드와 설계에 존재하는 도메인 문법, 상태 전이, 시간 계산, 데이터 소유권을 먼저 확인하고, 그 의미를 보존한 채 권위 저장 위치와 통신 경계를 서버로 옮긴다.

이번 초기 온라인 작업에서는 기존 자동항해 문법을 서버 계약으로 이관하기 전에, 표시 목적의 별도 `route` 형식을 만들었다. 이 형식은 접속 중인 플레이어의 화면 표현에는 사용할 수 있지만, 기존 `navLog`와 `START_AUTONAV` 문법을 대체하지 못한다.

이 문서는 같은 문제가 다른 도메인에서 반복되지 않도록 다음을 명시한다.

- 온라인 이관 시 반드시 보존해야 하는 원칙
- 클라이언트, Worker, D1, Durable Object, 스케줄러의 책임
- 기존 문법을 변경할 수 있는 조건
- 로그인과 로그아웃 상태의 정확한 의미
- 자동항해를 첫 기준 사례로 삼은 서버 계약 방향
- 구현 전에 사용자와 합의해야 하는 미결 사항

본 문서에서는 결정 상태를 다음과 같이 구분한다.

| 표기 | 의미 |

`제안`과 `미결` 항목은 개발자가 일반적인 관행이나 구현 편의를 이유로 임의 확정하지 않는다.

## 3. 핵심 원칙

### 3.1 온라인 이관은 의미 보존 작업이다

**확정**

- 기존 동작을 온라인으로 옮길 때 먼저 현재 코드의 상태, 이벤트, 계산식, 저장 구조를 조사한다.
- 기존 문법의 필드명을 그대로 쓰는 것보다 그 필드가 가진 의미와 상태 전이를 보존하는 것이 중요하다.
- 저장 위치가 브라우저에서 서버로 바뀐다는 이유만으로 게임 규칙을 다시 설계하지 않는다.
- 기존 규칙을 바꿔야 한다면 온라인 이관과 규칙 변경을 별도 의사결정으로 분리한다.
- 일반적인 MMO, 실시간 게임, Cloudflare 예제 구조는 참고 자료일 뿐 beta-void의 규칙보다 우선하지 않는다.

**금지**

- 기존 도메인 문법을 조사하지 않고 표준적으로 보이는 DTO를 새로 만드는 것
- 화면에 잘 보인다는 이유로 presence 데이터를 권위 상태로 승격하는 것
- 서버 구현이 편하다는 이유로 기존의 시간 파생 모델을 tick 기반 상태 갱신으로 바꾸는 것
- 명확하지 않은 부분을 코드로 먼저 결정한 뒤 사실상의 규칙으로 굳히는 것

### 3.2 서버 SSoT와 액션별 실행 경계를 함께 유지한다

**확정**

- 서버는 경제적으로 의미 있는 상태와 영속 계약의 단일 사실출처다.
- 클라이언트는 자유 수동 입력을 조작감과 화면 표현을 위해 즉시 실행할 수 있다.
- 결정론적 액션은 서버가 생성한 계약 없이 선실행하지 않는다.
- 서버는 결정론적 계약의 판정자이며 수동 이동의 재기준화, 파생, 결산 주체다.
- 경제 행위는 클라이언트 화면 위치가 아니라 서버 파생 상태를 사용한다.

### 3.3 권위 상태와 투영 상태를 구분한다

**확정**

| 계층 | 책임 | 책임이 아닌 것 |
| --- | --- | --- |
| 클라이언트 | 즉시 조작, 로컬 시뮬레이션, 렌더링, 명령 전송 | 영속 계약의 최종 판정 |
| Firebase Auth | Google 신원 증명, Firebase UID 제공 | 캐릭터 상태 및 게임 규칙 저장 |
| Cloudflare Worker | 인증 검증, 명령 수신, 도메인 규칙 실행, 서버 응답 | 프레임 단위 이동 시뮬레이션 |
| D1 | 캐릭터, 자산, 이동 계약, 결산 결과의 영속 SSoT | 실시간 소켓 fan-out |
| Durable Object | 접속 세션, 저지연 fan-out, 영역별 presence 투영 | 유일한 영속 항로 원본 |
| Scheduler/Alarm | 기한 도래 결산, 인덱스 정리, 배치 작업 | 모든 플레이어의 매초 위치 갱신 |
| IndexedDB | 캐시, 설정, 임시 로컬 선실행 상태 | 온라인 캐릭터의 최종 권위 상태 |

### 3.4 projection은 언제든 원본에서 다시 만들 수 있어야 한다

**확정**

presence, 목록용 캐시, 영역 인덱스, 클라이언트 스냅샷은 모두 projection이다.

projection은 다음 조건을 만족해야 한다.

- D1의 권위 레코드와 서버 시간으로 다시 만들 수 있다.
- projection 소실이 권위 상태 소실로 이어지지 않는다.
- WebSocket 종료가 이동 계약 취소를 의미하지 않는다.
- Durable Object 재시작이 자동항해 중단을 의미하지 않는다.
- projection 전용 필드가 도메인 규칙의 새 원본이 되지 않는다.

## 4. 온라인 이관 전 필수 절차

모든 도메인은 구현 전에 다음 산출물을 만든다.

### 4.1 현행 문법 목록

**확정**

- 상태 객체와 저장 레코드
- 명령 및 사용자 액션
- 상태 전이 조건
- 시간과 랜덤값의 출처
- 복원 우선순위
- 완료, 취소, 실패의 의미
- 다른 도메인과 연결되는 경제 결과

### 4.2 소유권 분류

각 필드를 다음 중 하나로 분류한다.

```txt
SERVER_AUTHORITY
SERVER_DERIVED
CLIENT_PREDICTION
CLIENT_PREFERENCE
EPHEMERAL_PROJECTION
STATIC_DEFINITION
```

분류되지 않은 필드는 서버 스키마나 온라인 메시지에 추가하지 않는다.

### 4.3 문법 대응표

기존 필드와 온라인 필드 사이의 대응표를 작성한다.

```txt
기존 필드
기존 의미
온라인 권위 필드
좌표계/시간 기준
변환 여부와 이유
호환 종료 조건
```

일대일 대응이 불가능한 항목은 임의 변환하지 않고 `미결`로 남긴다.

### 4.4 구현 승인 경계

**확정**

다음 상황에서는 코드 작업보다 사용자 합의가 먼저다.

- 기존 코드와 설계 문서가 서로 다를 때
- 같은 용어가 두 개 이상의 의미로 쓰일 때
- 서버 시간이 기존 로컬 시간과 다른 결과를 만들 때
- 로그아웃 상태의 진행이나 노출 정책이 불명확할 때
- projection을 만들기 위해 원본 문법에 없는 정보가 필요할 때
- 기존 동작의 오류처럼 보이는 부분을 발견했을 때

## 5. 인증과 접속 상태

### 5.1 상태 정의

**확정**

```txt
UNAUTHENTICATED
  유효한 Firebase 로그인과 캐릭터 세션이 없다.
  게임에 진입하거나 새 게임 명령을 발행할 수 없다.

AUTHENTICATED_ONLINE
  인증된 사용자가 게임에 접속해 있다.
  명령을 발행하고 실시간 presence에 참여할 수 있다.

AUTHENTICATED_CHARACTER_OFFLINE
  현재 브라우저 세션이나 WebSocket은 없지만 서버에 캐릭터가 존재한다.
  이미 기록된 시간 기반 계약과 세계 효과는 계속 유효하다.
```

“미로그인 플레이어의 자동항해”는 정확히는 `AUTHENTICATED_CHARACTER_OFFLINE` 상태의 캐릭터가 이미 기록한 자동항해 계약이 진행되는 경우를 의미한다.

### 5.2 인증과 시간 진행의 관계

**확정**

- 인증은 새 명령을 발행할 권한을 확인한다.
- 이미 기록된 계약의 시간 진행은 로그인 유지 여부에 의존하지 않는다.
- 로그아웃은 자동항해 취소 명령이 아니다.
- 소켓 종료는 자동항해 취소 명령이 아니다.
- 서버 계약을 변경하려면 인증된 새 명령이나 서버 도메인 규칙이 필요하다.

### 5.3 계정과 캐릭터

**확정**

- Firebase UID는 계정 신원을 식별한다.
- 항법, 자산, 진행 상태의 도메인 주체는 `character_id`다.
- 서버는 Firebase UID가 해당 `character_id`를 조작할 권한이 있는지 검증한다.
- 항법 로그와 이동 계약은 반드시 `character_id` 범위에 속해야 한다.
- 브라우저의 월드 공용 저장소에 캐릭터 구분 없는 활성 항로를 저장해서는 안 된다.

## 6. 자동항해 온라인 이관 계약

자동항해는 온라인 이관 원칙을 검증하는 첫 기준 도메인이다.

### 6.1 보존할 현행 의미

**현행**

현재 게임에는 다음 항법 문법이 존재한다.

```txt
navLog:
  id
  type
  issued_at
  from_position
  target
  flight_start_at
  peak_speed
  flight_duration
  status
  completed_at
  cancelled_at
```

현재 주요 `type`은 다음과 같다.

```txt
standard
hyperdrive
deactivation
```

현재 클라이언트는 `flight_start_at`, `from_position`, `target`, 비행 시간과 현재 런타임 `shipStats`를 이용해 재접속 시 위치와 속도를 결정론적으로 복원한다. 현행 `navLog`가 물리 파라미터를 고정 저장하지 않는 점은 이미 알려진 보완 대상이며, 온라인 이관 시 그대로 유지할 규칙이 아니다.

**확정**

- 이 결정론적 복원 성질을 서버 이관 후에도 유지한다.
- 자동항해 중 위치 체크포인트를 반복 전송하지 않는다.
- 자동항해 위치는 계약과 서버 시간으로 파생한다.
- 기존 가속, 순항, 감속 및 하이퍼드라이브 계산식을 먼저 고정 테스트한 뒤 서버 파생 함수로 공유하거나 이식한다.
- 물리 공식을 단순 선형 보간이나 일반적인 easing으로 대체하지 않는다.

### 6.2 좌표계 경계

**현행**

- 기존 `navLog`의 `from_position`과 `target`은 render-space를 사용한다.
- 서버 플레이어 위치와 월드 데이터는 data-space를 사용한다.

**확정**

- 서버의 정식 이동 계약은 data-space를 사용한다.
- render-space와 data-space 변환은 클라이언트 어댑터 경계에서만 수행한다.
- 좌표계 변경이 이동 거리, 도착 반경, 속도, 가속도 의미를 바꾸지 않도록 단위를 함께 변환한다.
- 메시지 안에서 두 좌표계를 혼용하지 않는다.

### 6.3 START_AUTONAV

**확정**

- 클라이언트는 `START_AUTONAV`를 전송하고 로컬 상태를 `pending`으로 둔다.
- pending 동안 목표 표식은 표시할 수 있지만 함선 이동, 회전, 속도와 항법 phase는 시작하지 않는다.
- 서버는 수신 시각의 권위 기준점과 함선 규칙으로 항로 계약을 생성하거나 명령을 거절한다.
- 수락 응답을 받은 클라이언트는 왕복 지연을 반영한 서버 현재 시각에서 계약 상태를 파생해 한 번만 적용한다.
- 거절 또는 판별 만료 응답을 받은 클라이언트는 pending을 해제하고 항로를 실행하지 않는다.
- 정상 응답 용어는 `accepted`, 실패 응답 용어는 `rejected` 또는 `expired`를 사용한다.

**제안: 클라이언트 이벤트**

```json
{
  "schemaVersion": 1,
  "command": "START_AUTONAV",
  "clientActionId": "ACT-...",
  "clientNavSessionId": "NAV-...",
  "clientSeq": 12,
  "clientSentAtMs": 123,
  "routeType": "standard",
  "start": { "x": 0, "y": 0, "z": 0 },
  "target": { "x": 1, "y": 2, "z": 3 },
  "shipSnapshot": {
    "maxSpeed": 0,
    "accelerationRate": 0,
    "decelerationRate": 0,
    "arrivalRadius": 0
  },
  "economyEpoch": "..."
}
```

`clientSentAtMs`와 클라이언트 `start`는 관측값이다. 서버 시간과 서버 기준점을 대체하지 않는다.

**제안: 서버 이동 계약**

```txt
movementContract:
  schemaVersion
  serverNavSessionId
  clientActionId
  clientNavSessionId
  clientSeq
  ownerCharacterId
  worldId
  routeType
  authoritativeStart
  target
  flightAt
  arriveAt
  shipSnapshot
  economyEpoch
  status
  canceledAt
  settledAt
  revision
```

**제안: 서버 응답**

```json
{
  "accepted": true,
  "command": "START_AUTONAV",
  "clientActionId": "ACT-...",
  "serverNavSessionId": "ROUTE-...",
  "flightAt": 123,
  "arriveAt": 456,
  "revision": 1,
  "correction": null
}
```

### 6.4 로그아웃 중 자동항해

**확정**

자동항해 계약이 서버에 기록된 뒤 접속이 종료되면 다음과 같이 처리한다.

```txt
WebSocket 종료
  -> live presence 연결만 종료
  -> movementContract 유지
  -> route 취소 이벤트 생성하지 않음
  -> 최종 pose로 route를 덮어쓰지 않음

시간 경과
  -> 매 tick 위치 저장하지 않음
  -> deriveMovementState(contract, serverNow)로 현재 상태 계산

재접속
  -> 서버 active movementContract 조회
  -> serverNow 기준 위치/속도/단계 파생
  -> 클라이언트 로컬 상태를 해당 계약에 연결
```

따라서 자동항해 중인 오프라인 캐릭터는 브라우저가 닫혀 있어도 서버 관점에서 계속 이동한다.

### 6.5 시간 파생과 스케줄러

**확정**

- 자동항해 진행을 위해 초 단위 스케줄러나 서버 tick을 만들지 않는다.
- 현재 위치는 `flightAt`, `arriveAt`, 시작점, 목표점, 고정 물리 스냅샷, `serverNow`로 계산한다.
- D1에는 계속 변하는 현재 좌표가 아니라 계산 근거가 되는 계약을 저장한다.
- 도착 결산은 조회 시 lazy settlement, 관련 경제 명령 수신 시 settlement, 또는 시간 버킷 기반 배치 작업으로 수행할 수 있다.
- 어떤 결산 방식이 선택되어도 같은 `serverNow`에서 같은 결과가 나와야 한다.
- `ARRIVED`는 항해가 목표 위치에 도착한 상태다.
- `DOCKED`는 별도의 정박 액션과 정박 규칙이 완료된 상태다.
- 도착은 자동으로 정박을 의미하지 않으며 `ARRIVED`와 `DOCKED`를 같은 상태로 취급하지 않는다.

#### 공통 저장소와 개별 항해 로직

**확정**

일반 자동항해와 하이퍼드라이브는 서로 다른 액션이며 물리 계산과 상태 단계도 다르다. 다만 둘 다 캐릭터가 발행한 항해 명령이므로 공통 저장소와 공통 계약 규칙을 사용할 수 있다.

통합 대상은 다음과 같다.

```txt
계약 ID와 멱등 키
ownerCharacterId / worldId
명령 발행 순서
routeType
시작점과 목표점
서버 시간 기준 시작/도착 시각
ACTIVE / CANCELED / ARRIVED 상태
revision
economyEpoch
```

통합 대상이 아닌 것은 다음과 같다.

```txt
일반 자동항해의 stopping / aligning / accelerating / cruising / decelerating
하이퍼드라이브의 cooldown / jump / warp entry / cruise / exit
각 항해 방식의 거리 및 속도 계산식
취소 가능 시점
항해 방식별 시각 효과
```

따라서 D1의 `movement_contracts`는 공통 envelope를 저장하고, `routeType`별 상세 물리 스냅샷과 파생 함수는 분리한다. 저장소 통합이 로직 통합이나 단일 보간 공식 사용을 의미하지 않는다.

#### 섹터 인덱스 갱신 방식

자동항해 함선을 다른 플레이어에게 보여주려면 “현재 어느 섹터에 속하는가”를 projection에 반영해야 한다. 권위 위치 자체는 계약과 `serverNow`로 언제든 계산할 수 있지만, 어떤 섹터 Durable Object가 해당 함선을 fan-out할지는 별도의 인덱스 문제다.

**선택지 A: lazy 갱신**

```txt
섹터 조회, 플레이어 접속, 주기적 snapshot 요청 시
  -> active movementContract 위치 파생
  -> 현재 섹터와 맞지 않는 인덱스 정리
  -> 현재 섹터 projection에 포함
```

장점:

- 섹터 경계마다 alarm을 만들지 않아 비용이 낮다.
- 오랫동안 아무도 관측하지 않는 섹터에는 작업이 발생하지 않는다.
- 인덱스가 잠시 오래되어도 실제 조회 결과는 서버 시간으로 다시 검증할 수 있다.

단점:

- 목적 섹터에 이미 접속 중인 관측자가 있어도 새 조회가 발생하기 전까지 함선 등장이 늦을 수 있다.
- 지속적인 관측자가 있는 섹터에는 낮은 빈도의 재조회 또는 갱신 신호가 필요하다.

**선택지 B: 경계 시각 alarm**

```txt
항로 계약 기록 시 섹터 경계 통과 시각 계산
  -> 해당 시각에 Durable Object alarm
  -> 출발 섹터에서 제거
  -> 도착 섹터 projection에 추가
```

장점:

- 이미 해당 섹터를 보고 있는 플레이어에게 비교적 정확한 시각에 등장시킬 수 있다.
- 별도 polling 없이 영역 이동을 push할 수 있다.

단점:

- 긴 항로와 많은 섹터 경계가 많은 alarm 및 인덱스 쓰기를 만든다.
- 항로 취소와 변경 때 예약 작업을 정리해야 한다.
- alarm 전달과 projection 갱신은 지연될 수 있으므로 여전히 권위 계산을 대체할 수 없다.

**선택지 C: 혼합**

```txt
권위 판정은 항상 lazy derive
도착 및 큰 영역 전환만 alarm 또는 시간 버킷으로 알림
세부 섹터 인덱스는 조회 시 교정
```

이 방식은 alarm을 정확성의 근거로 사용하지 않고, 현재 접속자에게 빠르게 알려주기 위한 최적화로만 사용한다.

**확정**

- 함선이 섹터 경계를 넘을 때 이전 섹터에서 갑자기 사라지는 표현을 허용한다.
- 섹터 사이의 연속적인 hand-off 애니메이션은 서버 정확성 요구사항이 아니다.
- 어떤 방식을 선택해도 섹터 인덱스는 projection이며 실제 위치는 이동 계약에서 다시 파생한다.

**미결**

- 이미 플레이어가 관측 중인 목적 섹터에 오프라인 항해 함선을 언제 나타낼지
- lazy 갱신만 사용할지, 큰 영역 전환에 한해 alarm/시간 버킷을 함께 사용할지

### 6.6 MANUAL_OVERRIDE

**확정**

- 수동 입력은 로컬 자동항해를 즉시 중단한다.
- 클라이언트는 `MANUAL_OVERRIDE` 기록 이벤트를 전송한다.
- `MANUAL_OVERRIDE`는 허가 요청이 아니다.
- 서버는 `MANUAL_OVERRIDE` 수신 시각의 항로상 위치를 새 수동 기준점으로 파생한다.
- 클라이언트가 보낸 위치는 관측값일 뿐 새 권위 기준점으로 그대로 저장하지 않는다.
- 서버가 반환한 기준점, 상태, revision이 항상 클라이언트 상태보다 우선한다.
- 이후 수동 이동은 `MOVE_CHECKPOINT` 문법을 사용한다.

#### 단순 처리 흐름

```txt
1. 사용자 수동 입력
2. active 자동항해가 있으면 클라이언트 시뮬레이션 즉시 취소
3. MANUAL_OVERRIDE를 서버 명령 큐에 추가
4. 서버가 현재 active movementContract 조회
5. serverReceivedAt 기준 항로상 위치 파생
6. 계약을 CANCELED로 기록하고 수동 기준점 갱신
7. 서버가 authoritativePosition과 revision 반환
8. 클라이언트가 서버 기준점으로 수렴
```

권장 payload는 작게 유지한다.

```json
{
  "command": "MANUAL_OVERRIDE",
  "clientActionId": "ACT-...",
  "serverNavSessionId": "ROUTE-...",
  "baseRevision": 3,
  "clientSeq": 13,
  "desiredSpeed": 500,
  "observedPosition": { "x": 0, "y": 0, "z": 0 }
}
```

`observedPosition`은 선택 필드다. 디버깅과 다음 검증 주기의 참고 관측으로만 사용할 수 있으며, 취소 자체에는 route ID와 서버 수신 시각만 있으면 된다. 서버가 취소 위치를 결정할 때 이 값을 권위 좌표로 사용하지 않는다.

#### 명령 순서 단순화

복잡한 pending tombstone이나 서버 명령 재정렬 대신 클라이언트의 항법 명령 큐를 직렬화한다.

```txt
START_AUTONAV가 아직 기록 중일 때 수동 입력 발생
  -> 수동 입력은 즉시 실행하고 pending 표시를 취소
  -> START_AUTONAV 수락 여부 판별을 먼저 정리
  -> 서버에 route가 생성되었다면 MANUAL_OVERRIDE를 정확히 한 번 전송
  -> route가 끝내 기록되지 않았다면 MANUAL_OVERRIDE도 전송하지 않음
  -> override 응답 또는 재접속 동기화에서 서버 기준점으로 변경
```

같은 action ID의 receipt를 조회하므로 응답을 잃었더라도 START가 서버에 기록되었는지 확인할 수 있다. START mutation 자체는 재전송하지 않는다. 서버는 명령 순서를 추측하거나 미래 명령을 기다리지 않는다.

서버는 `clientSeq`와 `baseRevision`을 사용해 오래된 명령이 최신 상태를 덮어쓰지 못하게 한다. 값이 현재 서버 상태와 맞지 않으면 명령을 억지로 병합하지 않고 현재 권위 상태를 반환한다.

#### ARRIVED 이후 override

**확정**

`serverReceivedAt >= arriveAt`이면 서버 상태는 이미 `ARRIVED`다. 이 경우 `MANUAL_OVERRIDE`는 과거 시점으로 소급하지 않는다.

```txt
서버:
  ARRIVED 상태 유지
  목표 위치를 authoritativePosition으로 반환

클라이언트:
  로컬 취소 표현을 폐기
  서버 ARRIVED 위치로 변경
```

클라이언트 시각이나 클라이언트 발생 시각을 근거로 서버 도착을 되돌리지 않는다.

#### override 직후 MOVE_CHECKPOINT

클라이언트의 수동 조작과 화면 이동은 계속 허용하되, `MANUAL_OVERRIDE`가 accepted되기 전에는 `MOVE_CHECKPOINT`를 전송하지 않는다.

```txt
override 기록 대기 중
  -> 수동 위치를 로컬에서 계속 계산
  -> 최신 관측 하나만 보관

override accepted
  -> 서버 기준점과 revision 적용
  -> 수동 조작이 완전히 정지할 때 최신 관측을 한 번 결산
```

이 방식은 서버 pending 저장과 순서 역전 병합을 제거한다. override 결과가 불명확하면 §6.9의 receipt 조회 규칙을 적용하고, 거절 또는 판별 만료 시 실패 상태를 표시한다.

### 6.7 MOVE_CHECKPOINT

**확정**

- 수동 이동 경로는 클라이언트의 표시 상태이며 주기적으로 서버에 기록하지 않는다.
- 수동 이동 또는 회전이 완전히 정지한 상태 전환에서 `MANUAL_STOPPED` 체크포인트를 한 번 전송한다.
- 정지 결산이 성공한 뒤에는 다시 움직이거나 다른 의미 있는 월드 사건이 발생할 때까지 위치 패킷과 D1 쓰기를 발생시키지 않는다.
- 도킹, 거래, 채굴, 건설, 섹터 전환처럼 위치가 경제 또는 월드 판정에 필요할 때에는 해당 행동 전에 별도 결산할 수 있다.
- 서버는 정지 결산의 `speed`와 `desired_speed`를 정확히 0으로 확정한다.
- 서버는 이전 권위 기준점, 서버 경과 시간, 함선의 최대 이동률로 도달 가능 범위를 검사한다.
- 서버는 클라이언트 경과 시간이 아니라 서버 수신 시각을 사용한다.
- 자동항해 중에는 `MOVE_CHECKPOINT`를 보내지 않는다.
- 브라우저 종료나 기록 실패로 최종 결산이 전달되지 않았다면 이동 경로를 복원하지 않고 마지막 서버 기준점으로 돌아간다.

### 6.8 presence와 자동항해

**확정**

presence는 이동 계약이나 필드 객체의 원본이 아니다.

beta-void의 함선, 자원, 건물 등 월드 오브젝트는 소유 플레이어의 로그인 여부와 무관하게 MMO 필드 위에 계속 존재한다.

```txt
로그인 상태
  -> 해당 캐릭터가 명령을 발행하고 직접 조작할 수 있는지 나타냄

함선의 존재 상태
  -> 서버 월드 상태에서 함선이 파괴, 이동, 보관, 정박되었는지 나타냄
```

따라서 플레이어가 로그아웃해도 우주 공간에 있는 함선을 필드에서 제거하지 않는다. active movement contract가 없는 정지 함선도 마지막 서버 기준점에 월드 오브젝트로 남는다. WebSocket의 `peer_left`는 접속 세션 종료만 의미하며 함선 제거 이벤트가 아니다.

실시간 표시 흐름은 다음과 같다.

```txt
D1 world object + movementContract
  -> 서버 시간으로 현재 이동 상태 파생
  -> 영역별 field/presence projection
  -> Durable Object fan-out
  -> 원격 클라이언트 렌더링
```

접속 중 수동 조작도 주기 pose를 보내지 않는다. 정지 시 최종 pose를 한 번 보내며, 이동 중 원격 표시는 마지막 결산 위치를 유지하거나 표시 전용 추정값을 사용할 수 있다. 자동항해는 권위 계약의 ID와 revision을 참조하는 projection을 사용한다.

정지한 브라우저 탭이 백그라운드로 전환되면 presence 연결과 필드 폴링을 중단한다. 다시 보이게 되면 현재 섹터 스냅샷을 한 번 받아 서버 기준으로 복구한다.

presence projection이 이동 공식을 새로 정의해서는 안 된다. 원격 클라이언트는 가능하면 로컬 플레이어와 같은 결정론적 항법 함수를 사용한다.

함선이 섹터 경계를 넘으면 이전 섹터 projection에서 즉시 사라져도 된다. 이 전환에는 이후 디지털 세계의 소멸/출현 연출을 적용할 수 있으며, 서버가 두 섹터 사이의 연속적인 렌더링 상태를 보장할 필요는 없다.

**현행 임시 구현**

현재 presence의 다음 형식은 표시 전용 임시 DTO다.

```txt
action_id
route_type
from_position
target
depart_delay_ms
duration_ms
```

이 형식은 다음 이유로 정식 이동 계약이 아니다.

- D1에 저장되지 않는다.
- WebSocket attachment 수명에 종속된다.
- 기존 항법 물리 스냅샷이 없다.
- 서버 계약 revision이 없다.
- `START_AUTONAV`, `MANUAL_OVERRIDE`, `MOVE_CHECKPOINT` 순서를 표현하지 못한다.
- 원격 렌더링이 기존 항법 공식 대신 단순 보간을 사용한다.

**확정**

- 현행 presence `route`를 권위 API로 확장하지 않는다.
- 정식 `movementContract`가 구현되면 presence는 해당 계약의 projection으로 교체한다.
- 실제 함선 모델 로딩, 이름표, 영역별 WebSocket fan-out은 재사용할 수 있다.

### 6.9 네트워크 실패

**확정**

- 결정론적 자동항해는 네트워크 응답을 기다리는 동안 실행하지 않는다.
- HTTP 오류처럼 서버 거절이 확인되면 즉시 실패 처리하고 pending을 해제한다.
- 전송 성공 여부가 불명확한 경우에만 같은 `clientActionId`의 receipt를 제한 시간까지 조회한다.
- START mutation 자체는 자동 재전송하지 않는다.
- 서버는 중복 `START_AUTONAV`에 새 계약을 추가 생성하지 않는다.
- 서버 응답은 `clientActionId`와 현재 pending 명령이 맞을 때만 적용한다.
- 제한 시간 안에 receipt를 확인하지 못하면 실패 상태를 화면에 표시하고 연결 상태를 오프라인으로 전환한다.
- 서버에 기록되지 않은 항로는 새로고침이나 재접속 시 복원하지 않는다.
- 오프라인 동안 서버 권위가 필요한 거래, 채굴, 정박, 계약 완료를 확정하지 않는다.
- 서버 연결이 복구되면 서버의 마지막 권위 기준점 또는 active contract로 변경한다.

권장 로컬 연결 상태:

```txt
ONLINE_RECORDED
  서버에 현재 항로가 기록됨

PENDING
  결정론적 이동을 시작하지 않고 최초 판정 응답 대기

DELIVERY_UNKNOWN
  mutation 응답을 잃어 같은 action ID의 receipt 조회 중

OFFLINE
  판별 시간 만료 또는 연결 단절, 명령 실패 표시

REBASING
  연결 복구 후 서버 기준점으로 변경 중
```

receipt 조회 횟수와 간격은 운영 튜닝값이다. 판별 제한 시간이 지나면 명령을 실패로 끝내며 나중에 자동 실행하지 않는다.

## 9. 자동항해 구현 전 승인 기준

다음 항목이 모두 충족되기 전에는 자동항해 서버 구현을 완료로 간주하지 않는다.

- [ ] 기존 `standard`, `hyperdrive`, `deactivation` 계산식에 고정 테스트가 있다.
- [ ] 기존 `navLog`와 서버 `movementContract` 대응표가 승인되었다.
- [ ] data-space 단위와 물리 파라미터 변환이 명시되었다.
- [ ] `START_AUTONAV` 이벤트와 멱등 키가 확정되었다.
- [ ] 서버 `flightAt`/`arriveAt` 산정 규칙이 확정되었다.
- [ ] 로그아웃 후 서버 시간 파생 테스트가 있다.
- [ ] 다른 브라우저와 다른 기기에서 동일한 파생 결과가 나온다.
- [ ] 같은 브라우저의 다른 캐릭터가 항로를 공유하지 않는다.
- [ ] WebSocket 종료 후에도 계약이 남는다.
- [ ] 자동항해 중 위치 패킷이 반복 전송되지 않는다.
- [ ] 수동 이동 중 위치 패킷과 D1 체크포인트가 반복 전송되지 않는다.
- [ ] 수동 이동에서 정지로 전환될 때 `MANUAL_STOPPED`가 정확히 한 번 기록된다.
- [ ] 정지 상태를 장시간 유지해도 추가 위치 기록이 발생하지 않는다.
- [ ] `MANUAL_OVERRIDE` 순서 역전 정책이 확정되었다.
- [ ] presence가 D1 계약 소실 없이 재구성된다.
- [ ] 로그아웃과 WebSocket 종료 후에도 필드의 함선이 사라지지 않는다.
- [ ] 서버 기록 실패 항로가 새로고침 후 복원되지 않는다.
- [ ] 연결 복구 시 실패한 로컬 항로가 서버 기준점으로 변경된다.
- [ ] `ARRIVED`와 `DOCKED`가 독립 상태로 검증된다.
- [ ] 도착 전 거래, 채굴, 정박 등 경제 행위가 서버 상태로 제한된다.

## 10. 단계별 이관 순서

이 절의 순서는 **항법 도메인 내부**의 이관 순서다. 프로젝트 전체의 선행 순서는 `09_HistoryV3_2SSoTAudit.md` 8절을 따른다. 즉, 동적 월드와 위치 기반 storage의 서버 원본을 먼저 마련한 뒤 이 절의 항법 이관을 진행한다.

### 단계 1: 현행 항법 고정

- 기존 항법 상태와 계산식을 테스트로 고정한다.
- `navLog` 필드, 좌표계, 복원 순서를 대응표로 작성한다.
- 캐릭터 구분 없는 로컬 `navLogs` 문제를 격리한다.

### 단계 2: 서버 이동 계약

- D1 `movement_contracts` 스키마를 정의한다.
- Worker에 `START_AUTONAV` 기록 경계를 만든다.
- 멱등성, client sequence, server revision을 적용한다.
- 서버 시간 기반 파생 함수를 구현한다.

### 단계 3: 복원 원본 전환

- 재접속 시 D1 active contract를 우선 조회한다.
- IndexedDB `navLogs`는 마이그레이션 입력 또는 임시 캐시로 격하한다.
- 다른 기기에서도 동일하게 복원되는지 확인한다.

### 단계 4: override와 수동 체크포인트

- `MANUAL_OVERRIDE`를 서버 계약에 연결한다.
- `MANUAL_STOPPED` 체크포인트를 서버 수동 기준점에 연결한다.
- 수동 이동 중 주기 pose와 주기 체크포인트를 제거한다.
- 순서 역전과 재시도를 검증한다.

### 단계 5: presence projection 교체

- 임시 WebSocket `route`를 서버 계약 projection으로 교체한다.
- 로그인 여부와 무관한 모든 필드 함선의 영역 노출 방식을 적용한다.
- 원격 렌더링을 기존 항법 파생 함수와 연결한다.

### 단계 6: 경제 결산 연결

- 도착 여부, 정박, 거래, 채굴, 생산의 서버 판정을 이동 계약과 연결한다.
- scheduler/alarm은 결산과 인덱스 유지에만 사용한다.

## 11. 결정 반영과 남은 논의

### 11.1 일반 자동항해와 하이퍼드라이브

**확정**

- 일반 자동항해와 하이퍼드라이브는 서로 다른 액션과 파생 로직을 유지한다.
- 둘 다 항해 명령이므로 공통 `movement_contracts` 저장소와 공통 envelope 규칙을 사용한다.
- `routeType`별 물리 스냅샷, 상태 단계, 취소 규칙, 파생 함수는 분리한다.

세부 구조는 §6.5의 “공통 저장소와 개별 항해 로직”을 따른다.

### 11.2 flight_start_at과 flightAt

두 필드는 의도상 모두 “정지와 정렬 같은 출발 준비가 끝나고 실제 항로 비행 계산이 시작되는 시각”을 나타낼 수 있다. 차이는 주로 누가 계산하고 어떤 시계를 권위로 삼는가에 있다.

| 항목 | 현재 `flight_start_at` | 제안된 서버 `flightAt` |
| --- | --- | --- |
| 계산 주체 | 클라이언트 `GameManager` | Worker의 항법 도메인 로직 |
| 시간 기준 | 클라이언트 `Date.now()` | 서버 수신 시각 및 서버 시계 |
| 시작 기준점 | 현재 로컬 함선 위치, 속도, 방향 | 서버 수동 기준점과 서버가 인정한 관측 |
| 신뢰 수준 | 로컬 시각화 및 복원 기준 | 경제 판정과 영속 항로의 권위 기준 |
| 재접속 범위 | 같은 브라우저 IndexedDB | 모든 기기와 다른 플레이어 |

현재 일반 자동항해는 대략 다음과 같이 계산한다.

```txt
클릭 시각
  + 현재 속도를 0으로 만드는 stopDuration
  + 목표 방향으로 정렬하는 alignDuration
  = flight_start_at
```

즉 `issued_at`은 명령을 만든 시각이고, `flight_start_at`은 실제 가속 비행이 시작되는 미래 시각이다.

서버 `flightAt`도 같은 상태 경계를 뜻하게 만들 수 있지만 값은 다음 이유로 달라질 수 있다.

```txt
네트워크 지연
클라이언트와 서버 시계 차이
클라이언트 관측 위치와 서버 기준점 차이
서버가 다시 계산한 정지/정렬 시간
```

**선택지 A: 서버 기준점에서 전체 pre-flight 재계산**

```txt
serverReceivedAt
  + 서버 기준 속도에서 계산한 stopDuration
  + 서버 기준 방향에서 계산한 alignDuration
  = flightAt
```

장점:

- 서버 상태와 물리 스냅샷만으로 결과를 재현할 수 있다.
- 클라이언트 시계를 신뢰하지 않는다.

단점:

- 클라이언트는 이미 stop/align을 진행했으므로 네트워크 지연만큼 서버 도착이 늦어질 수 있다.
- 서버가 방향과 현재 속도에 대한 충분한 기준 상태를 보유해야 한다.

**선택지 B: 클라이언트 계획을 관측으로 받아 서버가 보정**

```txt
클라이언트가 localFlightStartAt과 pre-flight 근거를 전송
서버가 clock offset, 수신 시각, 권위 기준점으로 허용 범위를 검증
검증된 남은 pre-flight만 serverReceivedAt에 더해 flightAt 확정
```

장점:

- 로컬 화면과 서버 도착 시각의 차이를 줄일 수 있다.

단점:

- clock offset과 “이미 진행한 pre-flight”의 신뢰 범위를 정의해야 한다.
- 검증 규칙이 복잡해진다.

**선택지 C: 수신 즉시 flightAt**

```txt
flightAt = serverReceivedAt
```

장점:

- 가장 단순하다.

단점:

- 기존 stopping/aligning 의미를 서버 계약에서 제거한다.
- 기존 문법을 충실히 옮긴다고 보기 어렵다.

**제안**

`flight_start_at`과 `flightAt`은 같은 상태 경계를 가리키되, 로컬 예측값과 서버 확정값으로 구분한다. 정확한 값 산정은 A 또는 B 중 하나를 선택하며 C는 기존 문법 보존 원칙상 사용하지 않는다.

**미결**

- 서버가 pre-flight를 처음부터 재계산할지
- 클라이언트가 이미 진행한 pre-flight를 제한적으로 인정할지
- 두 값 차이가 발생했을 때 UI ETA와 함선 표현을 즉시 변경할지 부드럽게 수렴할지

### 11.3 ARRIVED와 DOCKED

**확정**

```txt
ARRIVED
  항해 계약이 목표 좌표에 도착함

DOCKED
  별도의 정박 액션과 정박 규칙이 완료됨
```

`arriveAt`은 항해 계약의 도착 시각이다. `dockAt`은 자동항해의 다른 이름으로 사용하지 않는다. 도착한 함선은 정박 명령과 조건이 충족되기 전까지 우주 필드의 `ARRIVED` 함선이다.

### 11.4 서버 기록 실패

**확정**

- 서버 거절이 확인되면 즉시 실패 상태를 표시한다.
- 전송 결과가 불명확할 때에만 같은 action ID의 receipt를 제한 시간 동안 조회한다.
- mutation을 자동 재전송하지 않으며 판별 제한 시간이 지나면 오프라인 상태로 전환한다.
- 기록 실패한 자동항해는 새로고침 또는 재접속 시 복원하지 않는다.
- 서버 연결이 복구되면 서버 기준점으로 변경한다.

정확한 receipt 조회 횟수와 간격은 운영 튜닝 단계에서 정한다.

### 11.5 MANUAL_OVERRIDE와 START_AUTONAV

**확정**

- 수동 입력은 클라이언트 자동항해를 즉시 취소한다.
- START가 pending이면 로컬 자동항해는 아직 시작되지 않았으므로 pending 표시만 취소한다.
- 클라이언트는 현재 route ID와 수동 목표 속도를 포함한 `MANUAL_OVERRIDE`를 서버에 보낸다.
- 취소 위치는 클라이언트가 확정하지 않고 서버가 `serverReceivedAt`으로 파생한다.
- 항법 명령 전송은 클라이언트 큐에서 직렬화한다.
- START 판별이 진행 중이면 결과를 먼저 정리한 뒤, 수락된 경우에만 override를 정확히 한 번 보낸다.
- 서버는 오래된 revision을 병합하지 않고 현재 권위 상태를 반환한다.
- ARRIVED 이후의 override는 도착을 소급 취소하지 않는다.
- override 기록 전 수동 체크포인트는 전송하지 않고 최신 관측 하나만 보관한다.

따라서 서버는 미래 명령을 기다리는 tombstone이나 복잡한 순서 재조립을 기본 구조로 사용하지 않는다. 상세 흐름은 §6.6을 따른다.

### 11.6 로그아웃과 함선의 필드 존재

**확정**

- 함선, 자원, 건물 등 월드 오브젝트는 로그인 여부와 무관하게 MMO 필드에 존재한다.
- 로그아웃은 함선 despawn 이벤트가 아니다.
- 함선 visibility를 WebSocket 접속자 목록으로 결정하지 않는다.
- 정지한 오프라인 함선도 서버 기준 위치에 보인다.
- 자동항해 중인 오프라인 함선도 이동 계약에서 파생된 위치에 보인다.
- 파괴, 격납고 보관, 정박 내부 전환 같은 월드 규칙만 필드 노출 상태를 변경한다.

### 11.7 섹터 경계 통과

**확정**

- 함선이 섹터를 벗어나면 이전 섹터 화면에서 갑자기 사라져도 된다.
- 섹터 사이의 부드러운 네트워크 hand-off는 필수 요구사항이 아니다.
- 이후 디지털 세계의 소멸/출현 연출로 전환을 다듬는다.

**남은 결정**

- 목적 섹터에 이미 관측자가 있을 때 함선을 즉시 나타내기 위해 alarm을 사용할지
- 낮은 빈도의 sector snapshot 갱신으로 나타낼지
- 큰 영역 전환만 push하고 세부 인덱스는 lazy 교정할지

### 11.8 도착 결산

도착과 도착 결산은 구분한다.

```txt
논리적 도착:
  serverNow >= arriveAt이면 즉시 ARRIVED로 파생된다.
  별도 DB 쓰기나 scheduler 성공을 기다리지 않는다.

도착 결산:
  active 계약을 완료 상태로 materialize
  최종 서버 기준점을 목표 위치로 고정
  계약 revision 갱신
  영역 인덱스 정리
  도착 알림 또는 후속 작업 생성
  도착을 조건으로 하는 경제 명령의 기준 상태 제공
```

결산이 늦더라도 모든 서버 읽기와 경제 명령은 `serverNow`로 논리적 도착을 먼저 파생해야 한다. DB의 `status`가 아직 `ACTIVE`라는 이유로 도착 전 상태를 반환해서는 안 된다.

**선택지 A: lazy settlement**

```txt
캐릭터 조회
거래/채굴/정박 명령
섹터 snapshot
다음 항법 명령
```

위 이벤트가 발생할 때 도착을 발견하고 같은 D1 transaction에서 결산한다.

장점:

- 아무도 관측하지 않는 항로에는 도착 시각의 서버 작업이 없다.
- 계약 수가 많아도 timer 수가 늘지 않는다.
- 비용절감형 시간 파생 구조와 가장 잘 맞는다.

단점:

- 아무 이벤트가 없으면 materialized status와 영역 인덱스가 오래된 채 남는다.
- 접속 중인 다른 플레이어에게 도착 알림을 즉시 push하기 어렵다.

**선택지 B: 계약별 Durable Object alarm**

항로 생성 시 `arriveAt`에 alarm을 예약해 결산한다.

장점:

- 도착 시각 근처에 status, 인덱스, 알림을 갱신할 수 있다.
- 현재 관측자에게 push하기 쉽다.

단점:

- 활성 항로 수에 비례해 alarm 관리가 늘어난다.
- 취소, 항로 변경, 재시도 때 alarm revision 검증이 필요하다.
- alarm 지연이나 재실행을 고려한 멱등 결산이 여전히 필요하다.

**선택지 C: 시간 버킷 scheduler**

```txt
arriveAt을 분 단위/수분 단위 bucket에 등록
scheduler가 해당 bucket의 계약을 묶어서 결산
```

장점:

- 많은 계약을 묶어서 처리할 수 있다.
- 계약별 alarm보다 운영량을 예측하기 쉽다.

단점:

- materialized 결산과 알림이 bucket 간격만큼 늦을 수 있다.
- 버킷 재처리와 일부 실패에 대한 멱등성이 필요하다.

**선택지 D: 혼합**

```txt
정확성:
  모든 조회와 경제 명령에서 serverNow로 lazy derive

영속 결산:
  첫 관련 명령에서 transaction settlement

표시/알림/인덱스:
  시간 버킷 scheduler 또는 제한된 alarm으로 보조
```

혼합 방식에서는 scheduler와 alarm이 정확성의 원본이 아니라 projection을 적시에 갱신하기 위한 최적화다.

**제안**

비용과 정확성을 함께 고려하면 D를 기본 후보로 삼는다. 경제 판정은 언제나 lazy derive로 안전하게 만들고, 필드 인덱스와 알림이 필요한 범위만 배치 또는 alarm으로 보조한다.

**미결**

- 도착 알림과 필드 인덱스가 몇 초 또는 몇 분 늦어져도 되는지
- 계약별 alarm을 사용할 규모 기준
- 시간 버킷 간격
- 도착 시 자동으로 발생해야 하는 경제 후속 작업의 범위

### 13.2 의도적으로 남겨 둔 임시 경계

**미완료**

- 기존 `beta-void-dev`는 Worker에서 `LEGACY_DB`로 명시하며 프로필과 플레이어 JSON 스냅샷만 임시 보관한다.
- `/v1/player/assets`와 `/v1/player/ship-state`는 아직 정식 도메인 명령이 아니다.
- `docking_json`은 정식 도킹 권위가 아니며 제거 대상이다.
- IndexedDB의 `navLogs`, `gatheringLogs`는 현재 세션의 임시 로컬 동작을 위해 보존되지만 서버 권위가 아니다.
- Durable Object presence는 접속 중인 소켓의 표시 projection이며 로그아웃한 함선의 필드 존재를 아직 충족하지 않는다.
- 채굴, 거래, 도킹 등 로컬 월드 변경은 새로고침 시 서버 월드로 되돌아간다. 서버 경제 결과로 인정하지 않는다.

이 임시 경계를 이유로 클라이언트 JSON 업로드를 새 월드 권위 테이블에 연결하지 않는다. 다음 단계는 한 도메인의 현행 문법을 먼저 고정한 뒤 명령, 트랜잭션, 멱등성, projection을 함께 이관한다.

## 15. 2026-08-02 함선 배치 권위 계약

### 15.1 명령 수명

- 상태 변경 명령은 자동 재전송하지 않는다.
- 명령에는 `clientActionId`, `expectedRevision`, `issuedAt`, `expiresAt`을 포함한다.
- 서버가 명시적으로 거부한 명령은 즉시 최종 실패다.
- 응답이 유실된 경우 같은 명령을 다시 보내지 않고 `clientActionId`의 receipt만 조회한다.
- receipt 없이 `expiresAt`이 지나면 최종 실패로 확정하며, 서버는 만료 명령을 실행하지 않는다.
- 재접속 시 미기록 명령을 복원하지 않고 서버 배치 상태로 교정한다.

### 15.2 좌표와 custody

- `FIELD`와 `BETA_SPACE`에 배치된 함선만 독립적인 공간 좌표를 가진다.
- 건물에 정박한 함선은 독립 좌표를 갖지 않고 `ship_custodies`의 건물 소속 관계를 가진다.
- 정박 함선의 표시 좌표는 조회 시점의 건물 좌표에서 파생한다.
- 건물 좌표가 변경되면 소속 함선의 파생 표시 좌표도 함께 변경된다.
- `UNDOCK`은 서버가 현재 건물 좌표와 docking facing에서 새 필드 좌표를 만든 뒤 custody를 해제한다.
- `ARRIVED`는 이동 계약의 완료이고 건물 custody와 독립적이다.

### 15.3 Beta Space 귀환 기준점

- Beta Space 진입은 건물 정박이 아니며 함선은 별도 공간 `BETA_SPACE`의 좌표를 가진다.
- 서버는 진입 순간의 필드 위치, 회전, 속도를 `beta_space_sessions.return_anchor`에 불변값으로 저장한다.
- 세션 만료 시 source Beta Void의 현재 좌표나 세대를 조회해 귀환점을 다시 계산하지 않는다.
- 진입 후 Beta Void가 만료되어 다른 위치에 재생성되거나 재생성 대기 상태가 되어도 함선은 진입 당시 `return_anchor`로 돌아온다.
- 세션 만료는 로그인 여부와 무관하게 서버 시간에서 파생하며 다음 상태 조회나 명령에서 결산할 수 있다.

### 15.5 공간 모드와 이동 상태

- `ship_locations.spatial_mode`는 함선이 어느 공간 관계에 놓였는지를 나타낸다: `FIELD`, `DOCKED`, `BETA_SPACE`.
- `ship_locations.movement_phase`는 마지막으로 확정된 이동 상태를 나타낸다: `MANUAL`, `MOVING`, `ARRIVED`.
- 두 값은 독립적이다. 자동항해 도착 뒤 도킹하면 `spatial_mode=DOCKED`, `movement_phase=ARRIVED`가 될 수 있다.
- 도킹은 함선의 독립 좌표를 만들지 않는다. `ship_custodies`가 건물 소속을 보관하고 표시 좌표는 현재 건물 좌표에서 해석한다.
- 출항, 수동 체크포인트, Beta Space 진입·귀환처럼 새 배치가 확정되면 `movement_phase=MANUAL`로 전환한다.
- 새 자동항해 계약이 수락되면 `MOVING`, 서버 도착 결산이 끝나면 `ARRIVED`로 전환한다.

### 15.6 로그아웃 함선의 서버 정산

- 자동항해와 Beta Space 세션은 로그인 상태와 무관하게 서버 시간으로 진행된다.
- 소유자 상태 조회 외에도 구역 함선 목록과 관리자 요약·함선 목록 조회 전에 만료 계약을 lazy settlement 한다.
- 자동항해 도착은 계약을 `ARRIVED`로 바꾸고 목표 좌표를 함선의 서버 기준점으로 확정한다.
- Beta Space 만료는 현재 Beta Void 좌표나 generation을 사용하지 않고 진입 당시의 불변 `return_anchor`로 복귀시킨다.
- WebSocket presence는 수동 정지 직후의 짧은 표시 힌트만 제공한다. 자동항해 route는 D1 권위 계약에서만 생성하며 클라이언트가 다시 게시하지 않는다.
